# 大会データの保存・共有・復元

## 1. 対象と基本方針

初期リリースでは、大会入力と生成結果を利用者のブラウザ内へ保存する。サーバー側の
データベース、利用者アカウント、共同編集、公開閲覧リンクは使用しない。選手情報などの
個人情報は入力対象にしない。

保存データとJSONファイルは同じ`0.1.0` schemaを使う。クラウド基盤を変更しても、この
形式は変更しない。将来schemaを更新するときは、旧版を黙って読み替えず、移行処理と
後方互換性を別途定義する。

## 2. 自動保存と確定状態

- 入力変更から500ミリ秒後に、最新の下書きをIndexedDBへ自動保存する。
- 再読み込み時は下書きを優先し、下書きがなければ最後の確定状態を復元する。
- 「現在の内容を確定」を押すと、それまでの確定状態を「ひとつ前の状態」として残す。
- 保持する履歴は最新の確定状態と直前1世代だけとし、無制限に増やさない。
- 削除時は現在の内容を直前状態として一度だけ残し、「ひとつ前の状態へ戻す」で取り消せる。
- 保存容量不足やブラウザの保存機能を利用できない場合は、日本語でJSON保存を案内する。

## 3. JSONファイル

書き出しファイルには、文書種別、schema version、更新日時、大会名、入力、生成結果を含める。
ファイルは利用者自身が保管、複製、削除し、大会関係者間で受け渡す。

読み込み時は、現在のデータを変更する前に次を確認する。

- ファイルサイズが1 MB以下であること
- 文書種別とschema versionが対応していること
- 大会名と入力が存在すること
- 最大32チーム、16コート、512試合、128セクション以内であること
- チームID、コートID、試合IDが重複していないこと
- 試合が未登録チームや未登録の前提試合を参照していないこと
- 任意の`input.day2`に、開始時刻、試合時間、間隔、上限、休憩の整合した設定があること
- 任意の`result.day2_schedule`がトーナメント表の全実試合を重複なく配置していること
- 2日目の審判供給元、フォールバック理由、チーム経路、セクション時刻の参照が正しいこと
- `result.integrated_validation`が2日目日程内の統合検証記録と一致し、検証済みであること

検証に合格した場合だけ、大会名、チーム数、試合数をプレビューして置換確認を求める。
取り消した場合や検証に失敗した場合は、現在の保存内容を変更しない。置換前の確定状態は
直前1世代として残す。

## 4. 通信切断と障害時

- Service Workerはアプリシェルだけをcacheし、API応答や大会データをCache Storageへ保存しない。
- オフライン時は、保存済み大会、生成結果、印刷画面をIndexedDBから表示する。
- オフライン中の日程生成は行わず、通信復旧後の再試行を案内する。
- 生成が30秒で終了しない場合や通信に失敗した場合も、入力済みデータを保持する。
- ブラウザ保存が消失した場合はJSONファイルから復元する。サーバー側backupはない。

## 5. 利用者が行う操作

```text
大会名・チーム・会場を入力
  → 自動保存を確認
  → 日程生成
  → 結果確認・印刷
  → JSONファイルへ保存
  → 別端末ではファイルを選択
  → プレビューを確認して復元
```

初期化、削除、ファイルによる置換、直前状態への復元には確認を表示する。内部ID、JSON本文、
IndexedDB、schemaの技術用語は通常画面へ直接表示しない。
