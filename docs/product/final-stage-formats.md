# 決勝方式仕様

## 1. 目的と適用時期

本書は、1日目のブロックリーグ後に行う2日目の決勝方式について、対応する大会構成、
順位枠の作り方、審判、仮日程、保存形式、診断を定義する正本である。

決勝方式は1日目の日程生成前に利用者が明示的に選択し、結果を見てから変更してはならない。
決勝方式、トーナメント数、トーナメント名、端数処理方針のいずれかを変更した場合は、
1日目・2日目の生成結果、入力済み結果、最終順位をすべて無効化して再生成を求める。

新規大会と生成APIはschema `0.2.0`を使用する。本書でいう旧形式はschema `0.1.0`を指す。

## 2. 入力契約

決勝方式は次の判別可能なデータとして保存する。新規大会に既定の方式は設けない。

```yaml
final_stage:
  format: placement_tournament
  tournament_count: 2
  tournament_names:
    - 第1順位決定トーナメント
    - 第2順位決定トーナメント
```

```yaml
final_stage:
  format: same_rank_league
  uneven_policy: strict_same_rank  # strict_same_rank | merge_bottom
```

- `placement_tournament`では`tournament_count`を必須とし、`uneven_policy`を指定しない。
- `tournament_names`は省略可能とする。指定する場合はトーナメント数と同じ数の、1文字以上
  200文字以内の名前を順番に保存する。省略時は`第1順位決定トーナメント`から始まる既定名を使う。
- `same_rank_league`では`uneven_policy`を保存し、`tournament_count`を指定しない。
- 同順位リーグでチーム数がブロック数で割り切れない場合は、`uneven_policy`の明示選択を
  必須とする。
- 割り切れる場合は端数処理の選択を画面に表示せず、正規値として`strict_same_rank`を保存する。
  この場合の`merge_bottom`は受け付けない。
- schema `0.2.0`では`odd_split_policy`を使用しない。
- schema `0.2.0`では2日目の審判フォールバックを
  `day2_fallback: organizer | strict`として保存し、`tournament_fallback`を使用しない。
- schema `0.2.0`では互換性のため`organizer_capacity`を保存するが、その値は使用コート数以上を
  必須とし、実効値は使用コート数とする。Webでは利用者へ入力させず、使用コート数から導出する。
  公開生成APIは使用コート数未満をソルバー実行前に拒否し、超える値は使用コート数へ正規化する。

## 3. 順位決定トーナメント

### 3.1 対応構成

順位決定トーナメントは次の構成だけを受け付ける。

| 総チーム数 `T` | トーナメント数 `P` | 1トーナメントの人数 | 許可ブロック数 `B` |
| ---: | ---: | ---: | --- |
| 8 | 2 | 4 | 2、4 |
| 16 | 2 | 8 | 2、4、8 |
| 24 | 3 | 8 | 2、4、8 |
| 32 | 2 | 16 | 2、4、8、16 |
| 32 | 4 | 8 | 2、4、8 |

一般条件は次のすべてを満たすことである。

```text
B >= 2
T mod B = 0
(T / B) mod P = 0
```

上記以外のチーム数、トーナメント数、ブロック数を、予備戦、不戦通過、人数の異なる
順位帯、または暗黙の設定変更で補完してはならない。

### 3.2 順位帯

各ブロックの人数を`n = T / B`、1ブロックから1トーナメントへ送る順位数を
`m = n / P`、1トーナメントの人数を`S = T / P`とする。

1から始まる第`k`トーナメントは、全ブロックの次の順位枠を受け取る。

```text
ブロック内順位: (k - 1) * m + 1 から k * m
大会全体順位:   (k - 1) * S + 1 から k * S
```

各トーナメント内では、その順位帯の1位から最下位までを完全順位決定トーナメントで確定する。
異なるブロック間の得失点差や総得点はシード比較に使用せず、ブロック内順位の高い枠を
上位シード群とし、同じブロック順位は`random_seed`による再現可能な抽選で並べる。
初戦の同一ブロック対戦を最小化し、次に同一ブロック同士が再戦し得るラウンドを遅らせる。

新規生成する各トーナメントの人数は4、8、16のいずれかであるため、予備戦と不戦通過を
生成しない。

### 3.3 勝敗、審判、最終配置

- 通常得点が同点なら延長戦を行わず、3人制PKと以後1人ずつのサドンデスで勝者を決める。
- 通常得点とPK得点を別フィールドに保存する。
- 日の第1セクションと全トーナメントの決勝は主催者審判とする。
- その他の試合は、そのコートで直前に行われた実試合の勝者を原則として審判へ割り当てる。
- 直前試合の勝者を安全に割り当てられない場合、`day2_fallback: organizer`では理由を保存して
  主催者へ切り替え、`strict`では配置を組み直して実行可能解がなければエラーにする。
- 最高順位帯の決勝を、実試合がある最後のセクションへ必ず配置する。
- 他の順位帯の決勝は、使用セクション数の最小値を維持した上で、最後の実試合セクションとの
  最大差、次に差の合計を最小化する。

## 4. 同順位リーグ

### 4.1 対応構成

同順位リーグは総チーム数`4 <= T <= 32`、ブロック数
`2 <= B <= floor(T / 2)`で使用できる。1日目の各ブロックは2チーム以上とし、
ブロック間の人数差は最大1とする。

`q = floor(T / B)`、`r = T mod B`とする。安定したブロック順の先頭`r`ブロックを
`q + 1`チーム、残りを`q`チームとする。

### 4.2 厳密な同順位方式

`strict_same_rank`では、ブロック内順位`1`から`q`について、各順位の全`B`チームで
個別の1回総当たりを行う。各グループの全体順位範囲は次のとおりとする。

```text
順位 j のグループ: (j - 1) * B + 1 から j * B
```

`r > 0`なら、ブロック内`q + 1`位が存在する`r`チームだけで追加グループを作り、
全体`q * B + 1`位から`T`位を決める。`r = 1`なら実試合を作らず、その1チームを
全体`T`位へ自動確定し、警告を残す。

### 4.3 最下位グループ統合方式

`merge_bottom`は`r > 0`の場合だけ使用できる。ブロック内順位`1`から`q - 1`は、
厳密方式と同じ各`B`チームのグループとする。全ブロックの`q`位`B`チームと、存在する
`q + 1`位`r`チームを、`B + r`チームの最下位グループへ統合する。

最下位グループの全体順位範囲は次のとおりとする。

```text
(q - 1) * B + 1 から T
```

統合前のブロック内順位は優先せず、統合リーグの成績だけで範囲内の順位を決める。

### 4.4 18チーム・4ブロックの例

ブロック人数は5、5、4、4、`q = 4`、`r = 2`となる。

- `strict_same_rank`: 4、4、4、4、2チームの5グループを作り、全体順位範囲を
  1〜4、5〜8、9〜12、13〜16、17〜18位とする。
- `merge_bottom`: 4、4、4、6チームの4グループを作り、全体順位範囲を
  1〜4、5〜8、9〜12、13〜18位とする。

### 4.5 勝点、審判、日程

- 各グループで1回総当たりを行い、引き分けを認め、PKを行わない。
- 順位は1日目と同じく、勝点、得失点差、総得点、直接対戦、抽選の順で決める。
- 抽選は`random_seed`を使用し、候補と確定順を監査情報へ保存する。
- 日の第1セクションは主催者審判とする。それ以外のチーム審判は、
  直前セクションの同じコートで試合した2チームのいずれかだけから割り当てる。
- チーム審判を安全に割り当てられない場合は`day2_fallback`を適用する。
- 試合→審判は同じコートに限る。審判→試合は、直前の試合から審判を供給した
  試合→審判→試合の場合だけ許可し、後続の試合は別コートでもよい。審判→審判は許可しない。
  設定休憩の有無にかかわらずセクションは連続とみなし、空きセクションを挟んだ試合から
  審判を供給しない。
- 同順位リーグでは、特定グループの試合を最後のセクションへ固定しない。
- 使用セクション数、審判回数差、最大待ち時間、空きセクションを挟むコート移動、
  コート使用数の順で辞書式に最適化する。試合→審判→試合の回数と直前同一コートからの審判数は、
  ハード制約の監査値として保存する。

## 5. 仮対戦と確定

両方式とも1日目順位の確定前に仮対戦と仮日程を生成できる。参加者の正本は
`LeagueRank(block_id, rank)`とし、起こり得る全チーム割当てと、トーナメントでは全勝敗経路を
考慮して衝突と休憩を検証する。

順位確定後は、順位枠へ具体的なチームを注記するだけとし、試合ID、対戦構造、セクション、
時刻、コート、審判供給元を変更しない。

## 6. schema `0.1.0`との互換性

- 旧JSONは新しいアプリで検証後、閲覧・印刷専用として読み込める。
- 旧JSONの任意人数トーナメント、予備戦、不戦通過、`upper`／`lower`構造は、旧大会の
  表示に限って保持し、新規生成の仕様として扱わない。
- 利用者が編集用コピーへの変換を明示した場合、大会名、チーム、コート、1日目ブロック設定、
  手動割当て、日付・時刻、審判能力、`random_seed`、ソルバー上限を引き継ぐ。
- 変換時は1日目・2日目の生成結果、入力済み結果、最終順位、`odd_split_policy`、
  `tournament_fallback`を削除し、schemaを`0.2.0`にして決勝方式の再選択を求める。
- schema `0.1.0`の生成API要求は受け付けず、`SCHEMA_VERSION_UNSUPPORTED`を返して
  アプリ更新または編集用コピーへの変換を案内する。

## 7. 診断

| コード | 種別 | 発生条件 | 利用者向けメッセージ | 対応 |
| --- | --- | --- | --- | --- |
| `FINAL_STAGE_FORMAT_REQUIRED` | エラー | 1日目生成時に決勝方式が未選択 | 決勝方式を選択してください。方式は1日目の結果入力後には変更できません。 | 決勝方式を選ぶ |
| `PLACEMENT_TOURNAMENT_TEAM_COUNT_UNSUPPORTED` | エラー | トーナメント方式で`T`が8、16、24、32以外 | 決勝トーナメントは8・16・24・32チームに対応しています。 | チーム数を変更するか同順位リーグを選ぶ |
| `PLACEMENT_TOURNAMENT_COUNT_INVALID` | エラー | `T`に対応しない`P` | 参加チーム数に対応するトーナメント数を選択してください。 | 表示された候補から選ぶ |
| `PLACEMENT_TOURNAMENT_BLOCK_COUNT_INVALID` | エラー | 対応表または整除条件を満たさない`B` | この決勝トーナメント構成では選択したブロック数を使用できません。 | 表示されたブロック数から選ぶ |
| `PLACEMENT_TOURNAMENT_NAMES_INVALID` | エラー | 名前の数が`P`と異なる、空、前後空白、または200文字超過 | 各トーナメントの名前を1文字以上200文字以内で入力してください。 | 表示された名前を修正する |
| `SAME_RANK_LEAGUE_TEAM_COUNT_UNSUPPORTED` | エラー | `T`が4〜32以外、または`B`が2〜`floor(T/2)`以外 | 同順位リーグは4〜32チームで、各ブロック2チーム以上になるブロック数を選んでください。 | チーム数またはブロック数を変更する |
| `SAME_RANK_UNEVEN_POLICY_REQUIRED` | エラー | `T mod B != 0`で端数処理が未選択 | ブロック人数が均等でないため、最下位側のリーグの作り方を選択してください。 | 端数処理方針を選ぶ |
| `SAME_RANK_UNEVEN_POLICY_INVALID` | エラー | 割り切れる構成で`merge_bottom`を指定、または未知の方針を指定 | 選択した端数処理方針は、このブロック構成では使用できません。 | 表示された方針を選び直す |
| `SAME_RANK_UNEVEN_BLOCKS` | 警告 | `T mod B != 0` | ブロック人数が均等でないため、最下位側の同順位リーグの人数が他と異なります。 | グループ構成を確認して続行する |
| `SAME_RANK_SINGLETON_GROUP` | 警告 | 厳密方式で追加グループが1チーム | 最下位の同順位チームが1チームだけのため、試合を行わず順位を確定します。 | 自動確定される順位を確認する |
| `SCHEMA_VERSION_UNSUPPORTED` | エラー | schema `0.1.0`で生成APIを要求 | この保存データは旧形式です。アプリを更新し、編集用コピーへ変換してください。 | 閲覧を続けるか編集用コピーを作る |

警告は生成を阻害せず、入力確認画面、生成結果、保存JSONにコード、対象ブロック人数、
選択した端数処理方針、生成グループを残す。エラーでは既存の入力と結果を変更しない。
