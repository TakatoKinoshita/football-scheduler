# FaaS上でのOR-Tools技術検証

## 目的

OR-Tools CP-SATをスケール・トゥ・ゼロ可能なFaaSで実行し、地域サッカー大会の日程生成に必要な性能、再現性、診断能力、配布サイズ、運用費を満たせるか判断する。

この検証ではAWS Lambdaを最初の測定対象として用いるが、本番インフラとして採用する決定ではない。静的コンテンツ配信、計算基盤、永続化を含む本番構成は、実測値と利用要件が揃った後に別途比較し、ADRで決定する。

## 検証範囲

- Python 3.14とOR-Tools CP-SATを含むコンテナイメージのビルド
- FaaSに依存しない日程生成ロジックと薄いLambdaアダプター
- 固定fixtureによるローカル実行、コンテナ実行、SAMローカル実行
- 実際のFaaS環境でのコールド／ウォーム実行時間、メモリ、課金時間の測定
- 同一入力・同一シードでの再現性
- 独立検証器によるハード制約の再検査
- `OPTIMAL`、`FEASIBLE`、`INFEASIBLE`、`UNKNOWN`の区別
- 1実行および想定月間利用量に対する費用概算

完全な大会規則、2日目トーナメント、Web UI、永続化、本番向け認証・濫用対策はこの技術検証の対象外とする。

### この検証でモデル化する制約

- 全実試合の一意配置と、同一コート・同一セクションの容量
- 可能チーム集合を含む、同一セクションの試合／審判役割衝突
- 同じチームの連続セクション出場禁止
- 前提試合から後続試合まで2セクション以上の間隔
- 第1セクションと指定試合の主催者審判、主催者審判能力上限
- 上記を満たす範囲での使用セクション数最小化

リーグ審判回数の公平性、待ち時間、コート移動など、AGENTS.mdにある後順位の
ソフト制約はこの最小検証には含めない。独立検証器はソルバーの変数や制約式を
再利用せず、生成後のJSONから上記ハード制約を再検査する。

## 検証条件

### 固定入力

| fixture | 条件 | 用途 |
| --- | --- | --- |
| smoke | 4チーム、2コート、2試合 | 起動、入出力、コンテナ疎通の確認 |
| representative | 16チーム、4ブロック、3コート、リーグ24試合 | 代表規模の求解、再現性、制約検証、性能測定 |

代表fixtureでは`random_seed = 20260803`、`num_search_workers = 1`、ソルバー上限30秒を使用する。Lambda向けSAMテンプレートはx86-64、メモリ2,048 MB、関数タイムアウト45秒を使用する。予約済み同時実行数1を当初の条件としたが、検証アカウントのクォータでは設定できなかったため、公開トリガーを持たない構成で実測した。

実測時は、次の情報を結果と一緒に記録する。

- Git commit
- PythonとOR-Toolsのバージョン
- コンテナイメージのdigestとサイズ
- FaaSのリージョン、アーキテクチャ、メモリ、タイムアウト
- 入力fixtureのハッシュ、入力／出力バイト数
- `random_seed`、ワーカー数、ソルバー時間上限
- 測定日時と試行回数

## 成功基準

- Python 3.14とOR-Toolsを含むLambdaコンテナを再現可能にビルドできる。
- smokeとrepresentativeの両fixtureをローカル、Lambda Runtime Interface、SAMで呼び出せる。
- representativeを30秒以内に処理し、実行可能な日程を返す。
- 同一入力と同一シードの反復実行で、計測値を除く日程結果が一致する。
- 返された日程を独立検証器で検査し、対象としたすべてのハード制約に合格する。
- 解なしと探索時間切れを異なるstatusおよび日本語診断として返せる。
- 実FaaSでコールド／ウォーム実行時間、課金時間、最大使用メモリを取得できる。
- 1実行および想定月間利用量の概算費用を、料金表の参照日と計算式付きで示せる。
- 検証用デプロイが公開URLを既定で作らず、作成したクラウド資源を特定して削除できる。

## 測定方法

1. lockfileを固定して依存関係を同期し、lint、型検査、テストを実行する。
2. smokeとrepresentativeをローカルで実行し、status、ソルバーwall time、プロセス全体の経過時間、出力サイズを記録する。
3. 同じ入力を複数回実行し、計測値を除いた正規化結果のハッシュを比較する。
4. DockerのLambda Runtime Interfaceと`sam local invoke`で同じ入力を実行し、結果を独立検証する。
5. コンテナイメージの圧縮／展開サイズを記録する。
6. 承認された一時的な実FaaS環境へデプロイする。公開Function URLやAPI Gatewayは作らず、AWS CLIから直接invokeする。
7. 十分な休止後の初回をコールド候補、その直後の反復をウォーム候補として測定する。ログの初期化時間を確認し、推測だけで分類しない。
8. FaaSの公式メトリクスと実行ログから、duration、billed duration、最大使用メモリ、エラー、throttleを収集する。
9. 測定後にスタックとコンテナイメージを削除し、残存資源と課金アラームを確認する。

ローカルやSAMの結果は実FaaSのコールドスタート測定として扱わない。ネットワーク時間を含むクライアント側経過時間と、関数内／ソルバー内の時間も区別する。

### 配布サイズ

2026年8月5日にECRが報告した修正版イメージのサイズは289,536,096 bytes
（276.12 MiB）、digestは
`sha256:50f75e8a5d307c19eaf9cb85c191524122bccbb89fc206573b57a2f024c3f495`
だった。ローカルDockerが報告したサイズも約289.54 MBである。Python 3.14 Lambda

初回の実Lambda起動では初期化が10秒枠を一度超えた。一方、同じイメージを使った

大きいため、0.925秒だけを常に期待できるコールド性能として扱わない。

## 費用の計算式

料金は変わり得るため、評価時点の[AWS Lambda料金表](https://aws.amazon.com/lambda/pricing/)、
[Amazon ECR料金表](https://aws.amazon.com/ecr/pricing/)、対象リージョン、無料枠の
適用条件を記録して代入する。

```text
1実行の計算量（GB秒）
  = 割当メモリ（GB）× 課金対象時間（秒）

月間計算料金
  = max(0, 月間GB秒 - 適用可能な無料GB秒) × GB秒単価

月間リクエスト料金
  = max(0, 月間リクエスト数 - 適用可能な無料リクエスト数)
    × 100万リクエスト当たり単価 / 1,000,000

月額概算
  = 月間計算料金
    + 月間リクエスト料金
    + コンテナレジストリ保存料金
    + ログ保存・取り込み料金
    + データ転送料
    + 認証・レート制限等の付帯サービス料金
```

無料枠を前提に費用をゼロと断定しない。通常月、繁忙月、濫用時の少なくとも3シナリオで、呼出し回数と実行時間を変えて計算する。

### 2026年8月5日時点の実測値による概算

`us-east-1`、x86-64、2 GB、オンデマンド第1段階の計算単価
`$0.0000166667 / GB-second`、リクエスト単価`$0.20 / 100万回`、ECR保存
`$0.10 / GB-month`を使用した。無料枠、ログ、データ転送、税は含めない。

| 条件 | 計算式 | 1回あたり |
| --- | --- | ---: |
| ウォーム中央値 | `2 GB × 1.9155秒 × 単価 + リクエスト` | `$0.00006405` |
| 通常コールド | `2 GB × 2.876秒 × 単価 + リクエスト` | `$0.00009607` |
| 初回イメージ起動の観測値 | `2 GB × 17.027秒 × 単価 + リクエスト` | `$0.00056777` |

ECRの実測サイズだけを1か月保存すると約`$0.02895 / 月`である。全呼出しを
ウォーム中央値とした無料枠適用前の概算は、通常月100回で`$0.0354`、繁忙月
1,000回で`$0.0930`、濫用時10,000回で`$0.6695`（各ECR保存込み）となる。
公開APIを追加する場合は、この試算とは別に認証、レート制限、Bot対策の費用を加える。

## 確認済みの制約と未検証事項

- この検証のスケジューラは1日目リーグ戦の代表経路に限定しており、AGENTS.mdにある全大会規則の実装完了を意味しない。
- `num_search_workers = 1`は再現性を優先した検証条件であり、本番の性能最適値とは限らない。
- SAMとDockerのローカル実行では、実サービスの起動時間、ネットワーク、CPU配分、課金時間を再現できない。
- FaaSのstatusやタイムアウトと、CP-SAT自身のstatusを混同しないよう個別に記録する必要がある。
- Function URL、認証、レート制限、Bot対策、静的ホスティング、永続化方式は本番インフラ再評価の対象である。

## 実FaaSで判明した運用上の注意

- 検証アカウントの同時実行クォータでは、予約同時実行数1を設定すると未予約枠を
  最低10残せず、Lambda作成が拒否された。検証関数は公開トリガーを持たないため
  予約を外した。本番で公開入口を設ける場合は、クォータ、レート制限、課金上限を
  改めて設計する。
- ソースcheckoutのmodeがdirectory `700`、file `600`だったため、SAM localでは
  成功しても実Lambdaの非rootユーザーではimportできなかった。イメージ作成時に
  `/asset`へ`a+rX`を設定し、非rootコンテナでimportを検証するようにした。
- 作成したCloudFormation資源はLambda、IAM role、保持期間1日のLog Groupのみで、
  Function URLとAPI Gatewayは存在しない。SAM packaging用S3 bucketとECR repositoryは
  SAM管理資源として別途作成されたため、測定後に明示的な削除確認が必要である。

## 結論

### 検証資源の削除確認

2026年8月5日の測定後、SAMで検証スタック、Lambda、IAM role、Log Group、ECR
repository、ECR companion stackを削除した。versioning有効のSAM管理S3 bucketは、
今回作成されたテンプレート4 versionを指定して削除してから、管理CloudFormation
stackごと削除した。

削除後にCloudFormation、Lambda、IAM、CloudWatch Logs、ECR、S3を名前またはprefixで
検索し、対象資源がすべて空であることを確認した。検証用クラウド資源は残っていない。

AWS Lambdaコンテナは**条件付き候補**とする。代表規模は実Lambdaの全11回で30秒以内に
`OPTIMAL`となり、独立制約検証と再現性に合格した。ウォーム性能、最大メモリ、1回あたり
費用も初期検証の許容範囲である。

ただし、初回イメージ起動で10秒の初期化タイムアウトを観測し、アカウントの小さい
同時実行クォータでは予約同時実行を設定できなかった。実トラフィック、許容待ち時間、
濫用対策、運用主体が未確定なため、Lambda、他FaaS、コンテナ基盤、ブラウザ内求解を
本番インフラ再評価issueで比較してから採用を決定する。
